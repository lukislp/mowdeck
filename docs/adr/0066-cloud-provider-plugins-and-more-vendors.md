# ADR 0066: Cloud provider plugins and adapters for more vendors

## Status

Proposed (2026-10-29). Amends ADR 0012 (a second entry point group next to `mowdeck.connections`), ADR 0034 (linked accounts of any provider, credential fields instead of e-mail and password) and ADR 0011 (the GPL rule applies per vendor package). Open decisions are listed at the end; the plugin interface and the Mammotion refactor are ready to accept independently of them.

## Context

MowDeck reaches mowers through adapters behind `MowerConnection` (ADR 0012). Only Mammotion exists, and its account linking (ADR 0034) leaked into the core: the Device-Gateway imported `mowdeck-control-mammotion` directly (`cloud_accounts.py`, the fake cloud switch), the contracts had `CloudProvider.MAMMOTION`, Fleet sent `CloudProvider.MAMMOTION` and answered credential requests with Mammotion's option names (`account`, `password`), linked accounts were an e-mail and a password, and the web app's link form had exactly those two inputs. A second vendor would have needed changes in all of them.

The owner wants three more vendors researched and, where sensible, implemented: Husqvarna Automower, Segway Navimow and Worx Landroid. Hard constraints: no developer accounts, API keys or vendor logins are created or used now; everything is built and tested against recorded or handwritten fixtures and fakes; nobody can test on real hardware of these vendors. The end user is responsible for their own vendor account and credentials and enters them in MowDeck; the owner creates a vendor account only once a test device exists. Architecture rules (binding): core services (Device-Gateway, Fleet, Notifications, Telemetry, the web app) never import or special-case a vendor package; vendors plug in only through entry points; a new vendor is addable as a separate package without touching core code; safety stays in `MowerController`; GPL code stays isolated in its own package.

### Research per vendor (2026-10-29)

Versions and licences were read from PyPI and from the `LICENSE` file inside each sdist (the file wins where the two disagree).

**Husqvarna Automower** (also Gardena smart mowers sold through the same Husqvarna portal)

- Library: `aioautomower` 3.1.0 (2026-10-08), MIT, asyncio and aiohttp, typed (mashumaro data classes), maintained by the author of the Home Assistant core integration `husqvarna_automower`, which uses it. Alternative `automower-ble` 0.2.9 (GPL-3.0-or-later, BLE only, reverse engineered): not used, a cloud adapter covers more models and needs no radio near the garden.
- Packaging: MIT is permissive, so `mowdeck-control-husqvarna` can be Apache-2.0 like `mowdeck-control`.
- API: the official Automower Connect API (`api.amc.husqvarna.dev/v1`, REST, JSON:API) plus a websocket (`ws.openapi.husqvarna.dev/v1`) that pushes `mower-event-v2`, `battery-event-v2`, `position-event-v2`, `message-event-v2` and more. `AutomowerSession.get_status()` returns every mower of the account; commands: resume schedule, pause, park until next schedule or until further notice, park for a duration, start for a duration, start in a work area, set cutting height, set headlight mode, confirm an error, stay-out zone on/off, calendar.
- Auth and what the user provides: an **application key and application secret** from the Husqvarna Developer Portal (`developer.husqvarnagroup.cloud`). The user signs in there with their own Husqvarna account (the one of the Automower Connect app), creates an application, connects it to the "Authentication API" and the "Automower Connect API", and copies key and secret. MowDeck exchanges them with the OAuth2 client-credentials grant (`api.authentication.husqvarnagroup.dev/v1/oauth2/token`) for a bearer token that sees the mowers of that Husqvarna account. **This requires a (free) developer account on the user's side**; MowDeck needs no account of its own and stores no Husqvarna password. Home Assistant offers an authorization-code flow instead, which would need a MowDeck application registered by the operator; not chosen (see open decisions).
- Rate limits: 1 request per second and 10,000 requests per month per application key (Husqvarna's guidelines as quoted by several integrations; over the limit: HTTP 429 "Limit Exceeded"). Polling every 5 minutes uses about 8,640 requests a month, so the adapter must rely on the websocket for state and poll rarely (aioautomower's `REST_POLL_CYCLE` is 300 s).
- Capabilities: native mowing by schedule, by duration and by work area (models with work areas: `capabilities.work_areas`); no pattern parameters (stripe angle, spacing), so `native_patterns` is empty and `start_mow` maps to "start in work area" or "start for"; no manual driving; no camera; no RTK reporting in the API (EPOS models are RTK internally but the API does not say); GPS positions (the last 50 positions of the mower, models with `capabilities.position`); maps: only work area names and stay-out zone names, no geometry; cutting height 1 to 9 (a level, not millimetres) where `settings.cutting_height` is present; headlights on some models.
- Theft alarm (ADR 0027): the error table has "Mower lifted" (14), "Lifted" (15), "Upside down" (10), "Mower tilted" (33), "Alarm! Mower lifted" (71), "Alarm! Mower tilted" (72), "Alarm! Mower in motion" (73), "Alarm! Outside geofence" (74) and more. The adapter sets `raw.lifted` for 14, 15, 71 and 131 and passes the code as the lift code, so the theft alarm works without vendor knowledge in Telemetry. `raw.blade_on` is not reported; the adapter derives it from the activity (`mowing` implies blades on), marked as derived.
- State mapping: `MowerActivities` (`mowing`, `going_home`, `charging`, `leaving`, `parked_in_cs`, `stopped_in_garden`) and `MowerStates` (`in_operation`, `paused`, `restricted`, `error`, `fatal_error`, `off`, `stopped`, ...) map onto MowDeck's activities (mowing, returning, charging/docked, paused, error, idle).
- Verdict: **sensible; built first** (official, documented, permissive, push events).

**Segway Navimow**

- Library: `navimow-sdk` 0.1.2 (2026-04-10), import name `mower_sdk`, aiohttp plus MQTT (paho, aiomqtt). PyPI metadata says MIT, but the sdist's `LICENSE` file and its README say GPL-3.0: treated as **GPL-3.0**, so an adapter would be a separate GPL package like `mowdeck-control-mammotion`. The official HA integration `segwaynavimow/NavimowHA` uses it.
- API surface: device list, vehicle status (state and battery), commands start, stop, pause, resume, dock; MQTT status updates. Nothing else today (no map, no position, no errors beyond a state, no blade height, no zones); the README says more is "being added over time".
- Auth: the SDK does not authenticate ("you must obtain the access token separately"). The HA integration runs an OAuth2 authorization-code flow against Segway's login page with a client registered for Home Assistant (`client_id=homeassistant` and its secret in the integration's source). There is no public developer portal where a user or an operator could register their own client. Using Home Assistant's client from MowDeck would impersonate Home Assistant and is not acceptable; asking users to paste an access token works only until it expires (no refresh flow is documented).
- Verdict: **not sensible now; skipped.** It becomes sensible when Segway issues an OAuth client to MowDeck (operator registered) or publishes a developer portal; the provider plugin interface already supports it (an `oauth` credential flow would be added then, see consequences).

**Worx Landroid** (also Kress and LandXcape, same Positec cloud)

- Library: `pyworxcloud` 6.4.2 (2026-07-12), aiohttp plus MQTT over AWS IoT (paho), actively maintained, used by the HA custom integration `landroid_cloud`. PyPI metadata says MIT, but the sdist's `LICENSE` file is GPL-3.0: treated as **GPL-3.0**, separate GPL package `mowdeck-control-worx`.
- Auth and what the user provides: **the e-mail and password of the Worx (or Kress, LandXcape) app account** plus the brand. The library logs in with the vendor app's own OAuth client id (password grant, client ids in the library), like PyMammotion does for Mammotion. No developer account. As with Mammotion, a second account the mower is shared with avoids logging the phone app out.
- API surface: undocumented cloud API; state, error, battery, blade time, GPS (models with the RTK/GPS module), zones (up to 4 starting points, not geometry), rain delay, schedules, cutting height on some models (`set_cutting_height`), commands start, pause, home, safe home, edge cut, one-time schedule, zone training; push over MQTT.
- Rate limits and risk: Positec throttles API logins and has banned accounts that poll too often (the HA integration documents temporary bans after frequent reconnects). Push only, at most one login per account and gateway (shared session like ADR 0034), no polling loop.
- Theft alarm: the error codes "lifted" (2) and "upside down" (11) map to `raw.lifted` and the lift code; `raw.blade_on` follows the state (mowing, cutting edge, zoning).
- Verdict: **sensible**, with the same caveat as Mammotion (unofficial API, ban risk); built after Husqvarna.

## Decision

1. **Cloud provider plugins.** A vendor whose mowers are reached through a cloud ships a package that registers a `ProviderSpec` (in `mowdeck_control.providers`, Apache-2.0) in the entry point group **`mowdeck.cloud_providers`**; the entry point name is the provider id. The spec names the provider, whether it is on by default (`enabled_by_default`, only for providers tested on real hardware) and whether it also serves `cloud` registrations without a provider (`unqualified_cloud`, the cloud mowers from before this ADR; only Mammotion). `ProviderSpec.create(ProviderContext)` builds a `CloudProviderPlugin`: its `descriptor`, `discover(credentials)` (log in or reuse a session, list the devices, raise `CloudLoginRefused` or `CloudUnavailable`), `create_connection(config)` (one mower's `MowerConnection`, credentials in the options) and `close()`. `ProviderContext.fake` selects the package's fake cloud (development and browser tests); `cache_dir` is a private directory for session caches. The plugin stays a thin translator; `MowerController` keeps every safety rule (ADR 0012). The existing group `mowdeck.connections` is unchanged.
2. **Provider descriptors as contracts.** `ProviderDescriptor` (`mowdeck_contracts.v1.providers`): id, display name, summary, the credential fields (`CredentialField`: key, kind `text`, `email`, `secret` or `choice`, label, help, placeholder, required, pattern, maximum length, choices; exactly one field is the `identity`, at least one is secret), short setup steps, links to the vendor pages, `needs_developer_account` and `tested_on_hardware`. `ProviderDescriptor.problems()` is the one validation both Fleet and the gateway run. Descriptors are public data and never carry credentials.
3. **The gateway loads plugins, never vendor packages.** `device_gateway.adapters.control.providers` loads the enabled plugins (`MOWDECK_CLOUD_PROVIDERS_ENABLE` and `MOWDECK_CLOUD_PROVIDERS_DISABLE`, comma separated ids, on top of the defaults; disable wins), answers `gateway.cloud.providers` (`CloudProvidersRequest` → `CloudProvidersReply`, core NATS, queue `device-gateway`) and `gateway.cloud.discover` through them, and routes a `cloud` registration to the plugin named by its option `cloud_provider` (set by Fleet from the linked account); a registration naming a disabled provider is refused, never handed to another vendor. `MOWDECK_FAKE_CLOUDS` replaces `MOWDECK_FAKE_MAMMOTION_CLOUD` (the old name still works, both refused in production). `cloud_accounts.py` moved into the Mammotion package as its plugin (`mowdeck_control_mammotion.provider`); behaviour is unchanged (one session pool per gateway, the discovery reuses the mowers' session).
4. **Fleet stores any provider's credentials.** `CloudDiscoverRequest` carries `provider` (an id, no enum) and `credentials` (every field by key, excluded from `repr`); the ADR 0034 `email` and `password` stay as deprecated aliases the gateway maps onto the provider's identity and only secret field. `POST /linked-accounts` takes `{provider, credentials}`; Fleet asks the gateway for the descriptor (cached 30 s), checks the fields (422 with one problem per field, `credentials/<key>`, values never echoed; an unknown or disabled provider is 422 on `provider`), throttles failed logins per account, provider and identity (an HMAC of the secrets, never the secrets), seals the secret fields as one JSON object (AES-256-GCM, ADR 0034's key and scheme) and stores the other fields in `public_credentials`. Migration `0013` only adds `public_credentials` and `secret_format` (1: the ADR 0034 password, 2: the JSON object), so older rows keep working and move to format 2 the next time their secrets are sealed. `email` keeps its column name and holds the identity. `POST /{id}/sync` takes new secret fields (`credentials`, the deprecated `password` still works): a re-authentication; the account's mowers are re-published with a new `credentials_rev`. `fleet.mowers.credentials` answers a linked mower with every field of its account under the provider's keys. `GET /linked-accounts/providers` lists the enabled providers; responses carry `identity` and `public_credentials` (and `email` as a deprecated alias). Disabled providers are not listed; accounts of a provider that was switched off stay listed but cannot be read again (503) until it is on again.
5. **The web app renders the form from the descriptor.** Settings, Linked accounts (and the add-mower flow) show a vendor rail when several providers are enabled, the chosen provider's guidance (summary, setup steps, links, "untested on real hardware", "needs a developer account") and exactly its fields; each linked account shows its vendor, identity, status (connected, needs attention, provider not enabled), its non-secret fields, counts, last read and error, re-authentication with the provider's secret fields (never prefilled) and unlinking. No vendor is named in the app's code.
6. **An architecture test guards the boundary.** An adapter package declares `[tool.mowdeck.adapter] vendor-modules = [...]` in its `pyproject.toml`; `tools/repo-checks/tests/test_vendor_isolation.py` (the one vendor boundary check, shared with ADR 0067) fails when any non-test source of a service, a non-adapter library or an integration imports an adapter package, a declared vendor module or another dependency of an adapter (anywhere in the file), when a service other than the Device-Gateway depends on an adapter, and when an adapter registers neither `mowdeck.connections` nor `mowdeck.cloud_providers`, ships no `mowdeck.error_lexicons`, points an entry point into another package or imports another adapter. The former exception for `cloud_accounts.py` is gone with the file.
7. **Vendor adapters, one package each, off by default.** `mowdeck-control-husqvarna` (Apache-2.0, `aioautomower`) and `mowdeck-control-worx` (GPL-3.0, `pyworxcloud`), each with `tested_on_hardware: false`, `enabled_by_default: false`, unit tests against recorded payloads and a fake vendor client (no network), and a fake cloud for development and the browser tests. They land in their own pull requests after this one. Navimow is not built (see research).

### How to add a vendor

1. Create `libs/mowdeck-control-<vendor>` (Apache-2.0, or GPL-3.0 with its own `LICENSE` when the SDK is GPL, ADR 0011) depending on `mowdeck-contracts`, `mowdeck-control` and the vendor SDK pinned exactly.
2. Implement a `MowerConnection` (capabilities as data, state with `raw.lifted` and the lift code for the theft alarm, `raw.blade_on`), a `CloudProviderPlugin` and a fake cloud for `ProviderContext.fake`.
3. Register `[project.entry-points."mowdeck.cloud_providers"] <id> = "<package>.plugin:SPEC"`, ship the vendor's error lexicon under `mowdeck.error_lexicons` ([ADR 0067](0067-error-code-lexicon.md), `docs/dev/error-lexicon.md`) and declare `[tool.mowdeck.adapter] vendor-modules = ["<sdk module>"]`.
4. Add the package to the Device-Gateway's dependencies (the image's adapter set: packaging, not code) and to the workspace; no core module changes.
5. Operators enable it with `MOWDECK_CLOUD_PROVIDERS_ENABLE=<id>` until it was tested on real hardware.

The full checklist is `docs/dev/cloud-providers.md`.

Alternatives considered:

- *Keep `ConnectionKind` per vendor* (`husqvarna`, `worx`): rejected, the enum lives in the contracts, so every vendor would need a contract change, and the kind is a link type, not a vendor; one `cloud` kind plus the provider of the linked account keeps the registry open.
- *Fleet imports the descriptors from the adapter packages*: rejected, Fleet must not import vendor (possibly GPL) code; the gateway already owns the plugins and answers on the bus.
- *A separate secret store per provider*: not now; one sealed JSON object per linked account under the existing key is the same protection as before (ADR 0034).
- *An OAuth authorization-code flow for Husqvarna* (redirect through MowDeck): needs a MowDeck application at Husqvarna and a public redirect URL per installation; the client-credentials grant with the user's own application works for every self-hosted installation without either. Kept as an option for a hosted MowDeck.

## Consequences

- A vendor is a package and one dependency line in the gateway image; Fleet, the web app and the contracts do not change for it. The boundary test keeps it that way.
- The ADR 0034 API changed shape: `POST /linked-accounts` needs `provider` and `credentials` (the e-mail-and-password body is refused with 422); responses gain `identity` and `public_credentials`. The web app and the browser tests were updated; external API users must follow. Rollout: deploy the Device-Gateway before Fleet (an older gateway does not know `cloud_provider` in a registration).
- The Husqvarna adapter needs a developer account on the **user's** side (free, their own Husqvarna login); the link form says so and links the portal. Worx and Mammotion need only the app account.
- Untested adapters are labelled in the app and stay off until an operator enables them; nothing was tried against a real Husqvarna or Worx mower.
- Still vendor specific in core and left for follow-ups: the option catalogue of the `cloud` kind in Fleet (`fleet.domain.connections`: refresh intervals, cloud driving, the legacy own-login schema) describes the Mammotion adapter's options; per-provider mower options belong in the descriptor next (the texts are vendor neutral already). Comments and some UI texts (base stations, blade counter, camera data note, the setup tour) still name Mammotion where they describe Mammotion-only features.
- OAuth-based providers (Navimow, a hosted Husqvarna) need a redirect flow: a credential field kind `oauth` with an authorization URL and a Fleet callback is the planned extension; not built.

### Open decisions (owner)

1. Husqvarna: accept that users need their own (free) Husqvarna developer application, or register a MowDeck application for a hosted installation and add the authorization-code flow?
2. Navimow: ask Segway for an OAuth client for MowDeck (operator-registered), or drop Navimow until a developer portal exists?
3. Worx: accept the unofficial API and its ban risk for an opt-in provider (as for Mammotion), or wait for an official API?
4. When a test device exists: who tests, and when does a provider become `tested_on_hardware` and on by default?
