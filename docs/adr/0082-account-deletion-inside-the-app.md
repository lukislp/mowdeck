# ADR 0082: Deleting your own account inside the app

## Status

Accepted (2026-11-10). The investigation below showed that real deletion needs several pull requests; the maintainer decided the open points the same day. Step 1 (contract and Identity core) is implemented with this ADR. Steps 2a and 2b are implemented: Fleet, Scheduler, Telemetry, Planner and Entitlements (2a) and Notifications and Vision (2b) answer `account.erase.<service>` (see "How a service answers" below). Step 2c is implemented: Billing answers `account.erase.billing` (section 5), and since that was the last service the purge is **on by default** (section 4). Step 3 is implemented: a member deletes themselves with `DELETE /identity/me` (section 10). Step 4 is implemented: Settings -> Profile has the danger area and the app shell the banner of a scheduled deletion (section 9), so a user starts the deletion inside the app, in the browser and in the iOS and Android apps, which load the web app. The message streams are covered since the fix before step 2c (section 11): an erased account and a removed mower leave nothing in JetStream. Since the same fix no access token outlives a deletion (section 12): the purge asks no service before the account's tokens have expired, and a deleted user's tokens are refused by every service. Builds on [ADR 0057](0057-step-up-reauthentication.md) (re-authentication), [ADR 0076](0076-demo-sandboxes.md) (the purge calls of the demo sandboxes) and [ADR 0074](0074-nats-authentication-and-subject-permissions.md) (NATS permissions).

## Context

App Store guideline 5.1.1(v): an app that lets people create an account must let them start deleting it inside the app. Deactivation is not enough and the user's content has to go. MowDeck offers registration (`apps/web/src/routes/register`, linked from the sign-in page), so the iOS app needs an in-app path, and the same path is what the GDPR right to erasure needs on any installation.

### What exists today

**Identity's model.** Every user belongs to exactly one account: a registration creates the account, its owner user and a membership with `is_owner`; sub-users are created by an account admin and belong to that account (`memberships.add` appears only in the registration and in the creation of a sub-user). Owner and admin are fixed relations on the membership, the other rights are roles. Usernames and e-mail addresses are unique installation wide.

**Account deletion.** `DELETE /api/v1/identity/accounts/{account_id}` (permission `ManageAccount`, which means the owner) calls `AccountService.request_deletion`: the caller must send the password or, without it, have a recent step-up (ADR 0057); API tokens and service identities cannot (403 `step-up-unavailable`). It sets the account to `deleting`, `delete_after = now + IDENTITY_DELETION_GRACE_DAYS` (default 7), revokes the API tokens, ends the sessions of the other members, audits `account.deletion_requested` and answers 202. `POST .../restore` undoes it. **Nothing ever purges the account**: the docstring says "the purge after the grace period is a later job", and no code reads `delete_after`. So today the endpoint locks an account for good and deletes no data. The web app does not call it. The only complete cleanup of an account is the demo sandbox purge (ADR 0076).

**Removing a user.** `DELETE .../users/{user_id}` (`ManageUsers` plus step-up) deletes a sub-user (user row, sessions, passkeys and external identities by cascade) or removes a person's membership, audits `user.deleted` or `user.removed` and publishes `identity.user.deleted`. It refuses the owner and **refuses yourself** ("you cannot do this to yourself"), so a member has no way to remove themselves, and an owner cannot be removed at all. A person's user row is not deleted when the membership goes (only owned sub-users are), so a removed person's username, display name, e-mail and password hash stay in `users`.

**How other services learn about it.** `identity.user.deleted` is consumed by Notifications and Vision (durable consumers `notifications-identity` and `vision-identity`, both also on `identity.user.disabled`), which drop the user's own rows. Nobody consumes anything for a deleted account: Identity has no `identity.account.deleted` event. Fleet, Scheduler, Telemetry, Planner, Entitlements and Billing do not react to a deleted user or account. Seven services do have an idempotent "delete every row of this account" endpoint, `DELETE /api/v1/<service>/demo/accounts/{id}`, but it is the demo purge: it needs the demo seed secret and answers 404 outside demo mode.

### Why this takes several pull requests

A button on the strength of the existing endpoint would be dishonest: it only locks the account. Real deletion needs a purge job, a trigger every service answers, a new way for a member to remove themselves, a scrub of personal data in the audit log, the call to Stripe, and the web flow. That is several services with their own tests plus an Identity job with retries, and a UI that deleted only part of it must not ship. The work is split (below); each step is reviewed before the next starts, and the web flow comes last because it is the one that makes the promise.

## Decision

The maintainer decided the six open points on 2026-11-10; they are binding.

### 1. Two operations

- **Delete the account** (owner): the whole account and everything of it in every service.
- **Delete me** (a member without the owner relation, sub-users included): only the user, their membership and their personal rows. Step 3.

**One person, one account.** Both operations delete the user row, and with it the person everywhere. That is right because a user has exactly one membership: a membership is only ever created together with its user (a registration, a new sub-user; a test pins both the data and the two places in the source). The rule does not rely on it silently: `self_deletion_blocker` in `identity.domain.erasure` decides over *all* memberships of the person and refuses with 409 when there is one in another account. Owning another account: "delete that account first" (it would be left without an owner and never purged). A membership elsewhere: "leave that account first" (it would be removed without that account being told). `DELETE /identity/me`, the transaction that deletes a user and `DELETE /accounts/{id}` all apply it. Whoever adds a second way into an account (invitations) meets this refusal and has to decide what deleting such a person means; until then nothing is deleted across accounts.

**An owner of an account that still has other members cannot delete it.** The owner removes the members first (Settings -> Users); "Delete account" never removes other people implicitly. The API answers `409` and says how many members are left; the app (step 4) explains why and what to do. There is no ownership hand-over in the product (`promote_owner` is an operator command), so a hand-over is not part of this decision. The rule is `deletion_blocked_by` in the domain layer (`identity.domain.erasure`); other members count whatever their status, because a disabled member is still a person with an account row.

### 2. Re-authentication and who may call

Both operations need the step-up of ADR 0057 (password or passkey, in the native app the password) and a **login session**: API tokens and service identities get 403 `step-up-unavailable`, and a token is also refused by the owner check below. The existing `DELETE /api/v1/identity/accounts/{id}` keeps its body and its optional `password` field; a new `DELETE /api/v1/identity/me` (step 3) applies the policy by role so the client does not have to know which operation applies. The web flow (step 4) reuses the `StepUp` sheet, then an explanation, a typed confirmation and the date of the purge.

### 3. Grace period, cancelling, and the state machine

The grace period stays (`IDENTITY_DELETION_GRACE_DAYS`, default 7; 0 purges at the next sweep). The account moves through four states; only the first two are reversible:

```text
active --request--> deleting --grace over--> purging --every service confirmed--> erased
          ^             |
          +--- restore -+      (the owner, until the purge starts)
```

- **deleting** (`accounts.status`, `delete_after`): API tokens are revoked, and since a deletion needs the owner to be the only member there is nobody else to revoke. **The owner keeps every permission** (the `member` and `owner` tuples stay, as before this ADR), signs in and acts normally. The reason is the machine: the mowers keep running on their schedules during the grace period (the other services learn about the deletion only at the erasure), and an owner without permissions could not stop a mower, not even with the emergency stop, without restoring the account first. For a machine with blades that is not acceptable (maintainer decision of 2026-11-10). Two things are refused with 409 "the account is scheduled for deletion; cancel the deletion first" while the account is `deleting` or `purging`: adding a member (a member added now would be erased without being told, which would undo the 409 rule) and creating an API token (sub-users, API tokens, widget credentials and personal access tokens; a token could never be exchanged, token sync needs an active account). One guard in the application layer, `ensure_not_scheduled_for_deletion`, called by every use case that does either; invitations do not exist yet (the table is schema only), so there is no pending invitation to revoke, and the use case that accepts one must call the same guard. Stopping mowers, renaming, restoring and normal use stay allowed.
- **Cancelling.** Because nothing is restricted, cancelling needs no new mechanism: the owner signs in and calls `POST /accounts/{id}/restore` (the repeated `DELETE` answers 409 "already scheduled"), both with `can_manage_account` as before. Restore sets the account active again; the tuples never left. The restore and the start of the purge decide in one transaction each, so exactly one wins; once the purge has started, restore answers 409. **For step 4:** the web app must show a clear banner on every page while the account is `deleting`, "This account will be deleted on <date>", with a "Cancel deletion" button (the state and `delete_after` come from `GET /me`).
- **purging** (`accounts.status`, one `account_erasures` row): all sessions end, the tuples stay gone, the account is locked for everybody, there is no way back. The record names the services that must confirm, which did, the attempts and the next attempt.
- **erased**: the last service confirmed and Identity deleted its own rows in one transaction (the user, memberships, roles, tokens, passkeys, linked providers, sessions, devices, the account, the tuples). The `account_erasures` row stays as the proof (account id, times, services, counts; no personal data); `account.erased` is written to the audit log.

The rules (the transitions, the retry backoff, which accounts are due, which members block a deletion) are pure functions and the `AccountErasure` entity in `identity.domain.erasure`; the use case is `ErasureService` (`identity.application.erasure`); the bus is behind the `AccountEraser` port with `BusAccountEraser` as the adapter. There is no switch to turn deletion off.

### 4. The services are told over core NATS

Identity requests `account.erase.<service>` for each service with an `AccountEraseRequest{account_id, requested_at, reason}` and expects an `AccountEraseReply{ok, deleted, error}` (`libs/mowdeck-contracts`, `v1/erasure.py`, subjects in `v1/subjects.py`; the pattern of `entitlements.plan.set`, ADR 0031). Core NATS is reachable by services only (ADR 0074), so the request carries no principal. The permissions are in `tools/repo-checks/scripts/nats_auth.py`: Identity publishes `account.erase.*`, each service will serve its own subject in its step.

**Semantics every service keeps** (documented in the contract):

- **Idempotent:** erasing an account twice, or one the service never knew, is `ok=True` with `deleted=0`.
- **Retry safe:** a service that fails answers `ok=False` with a short `error`, or does not answer at all (NATS answers "no responders" at once when it is down); nothing is half acknowledged.
- **Completion is Identity's:** the reply is the confirmation. Identity stores it at once, never asks a confirmed service again, and deletes its own rows only after the last confirmation. An account that is gone from Identity is gone everywhere, and one that is not stays locked and visible.

**How a service answers (step 2a).** The part that is the same everywhere is in the service kit, once (`mowdeck_service_kit.erasure`), and a service adds only what it owns:

- The use case is `AccountErasure(purge, leftovers, forget)`. `purge` is the service's existing purge of the demo sandboxes (ADR 0076), reused, not written a second time. Afterwards the use case asks the store how many rows of the account are left, counted over **every table with an `account_id` column, read from the schema** (`account_tables` in `mowdeck_service_kit.db`), not over the list the purge deletes. Rows that remain raise `ErasureIncomplete`: a table somebody added and forgot in the purge makes the erasure fail loudly instead of confirming.
- The inbound adapter is `adapters/bus/erasure.py` of the service: it subscribes to its subject (queue group `<service>-erasure`, one replica answers) with the kit's `erasure_handler`, which decodes the request and always replies. `ok=False` for an invalid request, a purge that raised (the error names the exception class; the detail stays in the service's log) and for leftovers (the error names the tables and their counts, never row contents).
- A test per service proves the claim of the data map against the schema: every table without an `account_id` column is on a short list with its reason (Telemetry's thinning watermark, which goes with the mower; the plans and the feature catalogue of Entitlements, which are the installation's), and on PostgreSQL the seed must reach every account table before the erasure leaves none.
- The demo purge leaves what a process keeps of a sandbox to age out; a deleted account must not stay in memory. So the erasure also forgets what a use case keeps per account: Fleet's cached still images and its login throttle (the key holds the vendor e-mail address), the Scheduler's remembered mower statuses (they hold a position), and Telemetry's aerial rate limit plus its caches that are keyed by content, zone or session and cannot be searched by account (rendered widget maps, zone shapes, the map areas of tracking sessions), which are emptied. This reaches the replica that answers; another replica's entries end with their bound or the process.
- **Step 2b, Notifications and Vision,** hold more than rows, so their purge does more than delete (the details are in the READMEs of the two services):
  - *Work in flight.* Vision stops the analyses and executions running for the account **before** it deletes, so the row an interrupted analysis records is deleted with the rest; a request row that names a proposal is stored only while that proposal exists (decided with the insert under a row lock), so an analysis that another replica still runs writes nothing once the proposal is gone. Notifications cancels **after** the delete what it had already started: the deliveries its outbox had claimed (a queued message must not leave for an erased account) and the camera photos still being taken.
  - *Pictures.* Vision keeps the pictures a model saw in its database (`proposal_images`, no object storage). The table has no `account_id` column, so the count goes through the account's proposals: pictures or drive steps that remain make the erasure fail like any other row.
  - *Memory.* Fleet is asked first, so by the time Notifications is asked its rows no longer name the account's mowers: what it keeps per mower in memory (parsed geofence, area names, throttles) is dropped on `mower.removed`, not only by the purge. Vision's bus view also remembers the account of a mower it only saw commands of.
  - *Third parties.* Neither service calls a third party during an erasure (section 8). Notifications deletes the tokens, endpoints and the ntfy target, which is what ends the pushes; Vision sends nothing to a model.
- A purge of a large account can take longer than Identity waits for one request (`IDENTITY_ERASURE_TIMEOUT_SECONDS`). The service finishes it anyway, Identity records a failed attempt, and the next attempt is confirmed with `deleted=0`.

**Order and timing.** Nothing is asked before the access tokens of the account have expired (section 12; 11 minutes after the purge began with the defaults). The order is a rule of the domain, not the order a setting was written in: `ASK_ORDER` in `identity.domain.erasure` (the contract's `ERASURE_SERVICES`; a test keeps both equal), applied by `ask_order` when a purge begins and each time its open services are read, so also to a purge that was stored before the rule existed. It has two fixed places. Fleet is first: removing the mowers stops their simulators and connections. **Billing is asked before Entitlements** (step 2c): `entitlements.plan.set` creates the plan row of any account, and Billing sends it when the provider reports a subscription, so Entitlements erases only once Billing has confirmed that it has ended the subscriptions and applies nothing for the account any more. A Billing that fails or does not answer therefore also holds Entitlements back. After the first confirmation the others wait `IDENTITY_ERASURE_SETTLE_SECONDS` (30) so the mowers' last states have landed (ADR 0076 does the same). A failure doubles the wait (30 s, 60 s, ... at most 10 minutes). One attempt holds the purge with a five minute lease, so two Identity replicas do not run the same one.

**The purge is on by default since step 2c.** `IDENTITY_ERASURE_ENABLED` (Compose `IDENTITY_ERASURE_ENABLED`, Helm `config.IDENTITY_ERASURE_ENABLED`) was **false** while services did not answer yet (steps 1 to 2b): a purge that began before the services answer would end every session, remove every tuple and refuse restore (irreversible) and then hang. With Billing the registry's `PENDING` list is empty and the default is **true**; the repo guard encodes this and fails if the default is true while `PENDING` is not empty, or false while it is empty, in the settings, `.env.example`, the Compose file and the chart values alike. An operator can still set it to false: then nothing starts a purge, the purge task is not wired, and an account scheduled for deletion stays `deleting` and restorable, also after `delete_after`. The public demo stays off whatever the setting says.

**What turning it on does to accounts that are already scheduled.** There is one grace period, the one that started with the owner's request. An account whose `delete_after` has passed while the purge was off is purged at the first sweep after it is on (a sweep runs when Identity starts), like any other account whose grace period is over: it becomes `purging`, which cannot be undone, and its data is deleted once its access tokens have expired. Nobody is notified; the owner saw the date in the answer to the request and can restore the account until that sweep. No second grace period is added here (it would be a new mechanism; open point below). What exists so that nothing happens unseen: Identity says at start-up whether the purge is on, which services it asks and how many accounts are scheduled, and logs a warning that names the accounts past their grace period before the first sweep takes them; `python -m identity.cli erasures --scheduled` lists them with the purge on or off; and the operator documentation says how to look before updating and how to keep them (`IDENTITY_ERASURE_ENABLED=false`, or the owner restores).

**Which services are asked** is two settings and one rule (`required_services` in `identity.domain.erasure`). `IDENTITY_ERASURE_SERVICES`, default `fleet,scheduler,telemetry,notifications,vision,planner,entitlements`, names the services every installation runs. Billing is optional (most installations do not run it) and an unanswered subject would hold every purge back, so it is not on that list. It is not left to the operator either: Billing running and not asked would erase an account everywhere else and leave its customer and a running subscription at the payment provider. So **the deployment that enables Billing is what tells Identity** (step 2c): `MOWDECK_IDENTITY_OPTIONAL_SERVICES` names the optional parts the installation runs, and those of them that keep account data (today `billing`) must confirm too; other names are ignored. Compose passes `COMPOSE_PROFILES` there, the chart `billing` when `services.billing.enabled`. Billing gets the same value (`MOWDECK_BILLING_OPTIONAL_SERVICES`) and its container **refuses to start** when `billing` is not in it, which closes the one way the two could still differ: `docker compose --profile billing` on the command line starts the service without setting `COMPOSE_PROFILES`. An installation without Billing names nothing and its purges never wait for it. With the switch on and a listed service that does not answer, Identity keeps the account in `purging` and logs the failure: **it never deletes its own rows while a listed service has not confirmed**. A guard test (`tools/repo-checks/tests/test_erasure_registry.py`) kept the services that own tables and did not answer yet as `PENDING` with their step; the list is empty since step 2c and stays empty, and a new service with tables that does not answer fails the test. The same file checks the deployment: the default list is exactly the erasure services without a Compose profile, a profile is named like its service, Compose gives Identity and Billing the same variable, and the chart derives both from its own toggle.

**What the operator sees.** The record is `python -m identity.cli erasures [--all]`: state, services confirmed of those required, attempts and the last error. A failing step logs a warning on every attempt, and an error once the purge is older than `IDENTITY_ERASURE_STALL_HOURS` (1): "the account is locked but not deleted".

### 5. Billing

Billing (step 2c) ends the open subscriptions at the provider **and deletes the customer there**. Invoices the provider must keep stay with the provider; Billing keeps no invoice data of an erased account, and the privacy text and the operator documentation say so. Billing is optional: where it does not run it is not asked (section 4).

**At the provider,** through the port `PaymentProvider` and nowhere else (`cancel_subscription`, `delete_customer`; the Stripe adapter and the fake implement both):

- Every subscription of the account that Billing knows as open ends **now**, not at the period end: `DELETE /v1/subscriptions/{id}` with `invoice_now=false` and `prorate=false`. No final invoice is created, no credit for the unused time, and **nothing is refunded**: this ADR decides no refund, so the erasure issues none. The rest of a period that was already paid is lost to the customer; the dialog of step 4 has to say so (open point below).
- Then the customer object is deleted (`DELETE /v1/customers/{id}`), with what the provider stores on it: name, e-mail address, addresses, tax ids, payment methods. Deleting the customer also ends any subscription Billing never heard of (a webhook that never arrived).
- **What stays at the provider:** the invoices, payments and their records, which it must keep by law and keeps under its own terms. They are no longer reachable from MowDeck (the invoice links were in the rows that are deleted).
- Both calls are idempotent: a subscription that has ended already, and a subscription or a customer the provider no longer knows (Stripe's `resource_missing`), count as done.
- **A provider error fails the erasure.** A rate limit, a timeout, a connection error and a 5xx (after the SDK's own retries) are `ProviderUnavailable`, everything else `ProviderError`; either way Billing answers `ok=false`, deletes no row and Identity asks again with its backoff. Billing never confirms while the customer may still exist.
- Rows of another provider than the configured one cannot be finished: the erasure fails rather than leave a customer behind. The exception is the fake provider of tests and demos (`LOCAL_PROVIDERS` in `billing.domain.erasure`), which keeps nothing anywhere; its rows are deleted without a call.

**In Billing's database,** afterwards and in one transaction. The provider comes first because the rows are what names the customer and the subscriptions: a failed provider call leaves them, and the next attempt knows what to end and delete (the rule of step 2a, "rows still name what must be purged"). Billing has no purge of the demo sandboxes to reuse (the demo does not run it), so `billing.application.erasure.AccountPurge` is the one place.

| Table | Of an erased account | Why |
| --- | --- | --- |
| `accounts` | deleted | the account's name and kind |
| `customers` | deleted, after the provider confirmed | the link between the account and the provider's customer id |
| `subscriptions` | deleted | plan, status, period ends |
| `invoices` | deleted | amounts, numbers and the links to the provider's hosted pages: Billing keeps no invoice copies |
| `webhook_events` with the account's id | deleted | the ledger of the account's provider events |
| `webhook_events` without an account | kept | events of customers Billing does not know and ignored types. A row is the provider's event id, its type, times and the outcome. **No payload is stored**, so no e-mail address and no name, although the events carry them (a test pins the columns) |

Every table has an `account_id` column, none is keyed by a provider id alone, and there is no table of checkout sessions or idempotency keys (the customer's idempotency key is derived from the account id and sent, not stored). The leftover count of step 2a covers all five. Billing keeps nothing of an account in memory (its one cache holds the provider's prices).

**Provider events after the erasure.** The provider answers the cancellation with `customer.subscription.deleted` and the deletion with `customer.deleted`, retries undelivered events for days, and the subscription events carry the account id in their metadata. Before step 2c that metadata was enough to apply an event, which would have written the customer and the subscription again and set a plan in Entitlements. Now **the customer row decides whose event it is**: Billing creates the provider's customer of an account itself, before the first checkout, so an event whose customer it does not know is nobody's. It is acknowledged (200, outcome `unknown_account`, a ledger row without an account) and dropped, whatever its metadata says; `customer.deleted` is an ignored type. An event that arrives *while* the erasure runs is applied under a lock on its customer row (`Tx.lock_customer`: `SELECT ... FOR UPDATE`), held while Entitlements is asked, and the erasure deletes the customer rows first, under the same lock: the event finishes completely (plan, row, published event) before the rows go and before Billing confirms, or it finds no customer.

**The order with Entitlements** is guaranteed in one place, Identity's `ASK_ORDER` (section 4): Billing confirms before Entitlements is asked. Billing's part is only that it applies nothing for a customer it no longer knows; the erasure itself sets no plan and publishes nothing.

### 6. Audit log: rows stay, personal fields go

The audit logs are append-only by trigger (ADR 0076 added the one exception, the demo purge's `DELETE`). A deletion keeps its audit rows and removes their personal fields, through the **one sanctioned path** the trigger allows, defined in migration 0011:

- The trigger `audit_log_append_only()` lets an `UPDATE` pass only while the transaction-local setting `mowdeck.audit_scrub` is `on` **and** the new row differs from the old one in nothing but removed personal data: every column except `actor_name`, `ip` and `details` is equal (`IS NOT DISTINCT FROM`), `actor_name` and `ip` become NULL, and the new `details` is contained in the old one (`old @> new`, so it can only lose keys). Anything else, with the flag or without, raises "audit_log is append-only"; a `DELETE` still needs the demo purge's flag.
- Only the database function `audit_log_scrub(account_id)` sets the flag, and it clears it again before it returns, so a later statement of the same transaction is refused again. It keeps only the `details` keys on the allow list (ids, counts, kinds, times: `AUDIT_DETAILS_KEPT` in `identity.domain.erasure`; the migration holds the same list and a test compares both) and drops every other key, so a key a future action adds is scrubbed until someone lists it. The function is idempotent.
- The Python side is `Tx.scrub_audit(account_id)` (SQL: the function; memory: the same filter).
- The integrity protection is not weakened for anything else: no flag, no change; the demo purge's `DELETE` is untouched. Tests on PostgreSQL cover the function, every refused variant (with and without the flag) and that the flag does not leak out of the function.

**One user (step 3).** A member who deletes themselves leaves an account that goes on, so only the rows about that user are scrubbed: the rows the user acted in (`actor_subject = user:<id>`) and the rows whose target is the user. Migration 0012 adds `audit_log_scrub_user(user_id)`, the second and only other function that sets the flag, with the same allow list. Some of those rows were written by somebody else (an admin created, renamed or disabled the user): there the name and the address are the admin's and stay, only `details` loses its personal keys. For that the trigger's rule for `actor_name` and `ip` becomes "each stays as it is or becomes NULL" (it was "both become NULL"); nothing can be added or changed, as before. The name and address go when the user acted, and when nobody is named as the actor (a sign-in: the address is the one the user came from). The rule is `audit_fields_after_user_scrub` in `identity.domain.erasure` (the memory store uses it; a test on PostgreSQL compares the function with it), the Python side `Tx.scrub_user_audit(user_id)`.

The final row `account.erased` carries ids, counts and the services, no personal data. Opaque `created_by` ids in other services stay: once Identity's user row is gone they identify nobody. Other services' audit logs (Fleet's) are handled in their step. **Step 2a, Fleet:** the account's rows of Fleet's `audit_log` are deleted with the rest, through the `DELETE` its trigger already admits for the purge (migration 0014 of Fleet, ADR 0076), not scrubbed. Fleet's log is the account's own record of what happened to its mowers, sites and groups; once the account is gone nobody may read it, and the proof that the deletion happened is Identity's `account_erasures` row and its `account.erased` audit row.

### 7. Backups and the dialog text

There is no defined backup retention today (the operator's `pg_dumpall` before updates, [Compose](../ops/compose.md)), and backups are a separate topic the maintainer will take up later. **No retention is invented here.** The in-app dialog, the privacy template and the operator documentation say truthfully that backups made by the operator may still contain the data until they are rotated out and that the retention is up to the operator. Step 4 adds that text, with a clearly marked TODO in the operator documentation ([Compose](../ops/compose.md), "Long-term backups are yours for now") and the privacy template (`apps/web/static/legal/privacy.md`, section 6) for the operator's retention statement. The dialog says: "Backups made by the operator of this server may still contain the data until they are replaced. How long they are kept is up to the operator."

**What the text may say about the message bus (section 11).** For a deleted *account*: when the deletion has finished, the internal message streams hold nothing of the account any more (what remains are technical notices that carry random ids and no content, for at most 30 days). For a member who deletes *themselves*: the name is removed from the account's records at once; in the internal record of sent commands it can remain for up to 24 hours and in the internal record of camera sessions for up to 30 days, then it is gone automatically. The text must not promise less time than these two maxima.

### 8. Third parties

- **Stripe:** see 5.
- **APNs:** the app removes its registration on sign-out (`nativeShell.signingOut()`), and the purge deletes the rows, so no push goes to the device again. The same holds for the other push targets Notifications stores (step 2b): the Web Push endpoint and keys and the ntfy server, topic and token are deleted and nothing is sent to them again; MowDeck does not ask the browser's push service or the ntfy server to delete anything. What they hold (the browser's subscription until the browser drops it, messages an ntfy server still caches) is theirs, like a push that was already delivered.
- **Vendor clouds** (Mammotion, Husqvarna, Worx): MowDeck removes the stored credentials with the linked account and cannot delete what the vendor holds. The in-app text and the privacy text say so.
- **Cloud AI provider** ([ADR 0081](0081-explicit-consent-before-cloud-ai.md)): a request already sent stays with the provider under its terms; MowDeck deletes the pictures and keys it stores.

### 9. Web app (step 4)

Settings -> Profile gets a separate danger area under the sign-out ("Delete account" or "Delete me" by role, the explanation, the member count, a blocked state with its reason, the date of the purge, "Cancel deletion" while it is scheduled, `DemoLock` in the demo). The flow is a lib service (no rules in the component): load what applies, step-up through the existing controller, call the endpoint, then the same clean exit as sign-out (`nativeShell.signingOut()` first so push tokens and widget credentials go, then the session logout). Component and unit tests cover pending, error, blocked and demo-locked.

**Implemented (step 4).** What the web app needs is in `GET /me`, so neither the danger area nor the banner on every page sends a request of its own. The app (`apps/web/src/lib/account-deletion`, [Web app](../dev/web-app.md#deleting-your-account)):

- `AccountDeletion` calls `DELETE /me` for both roles, without a password: the step-up sheet opens through the API client when the last confirmation is older than the window (ADR 0057), and a dismissed sheet is no error. Before the call the user types their user name. For `operation: "user"` the app leaves through `signOut('deleted')`, the one sequence the sign-out button uses too (`nativeShell.signingOut()`, the demo visitor flag, the session, the login page with "Your user has been deleted"); the access token is refused by then, so the shell's server calls fail and it still forgets the push token and the widget credential on the device, while Notifications and Identity have deleted both rows. For `operation: "account"` it reads `/me` again and the banner appears. `restore()` is `POST /accounts/{id}/restore`, which needs no step-up.
- `AccountDeletionPanel.svelte` and `DeletionBanner.svelte` only render. - The texts follow sections 7 and 8 (immediate and final for a member; what stays without the name; schedules that stop; share links that stop; access ending at once or with the current sign-in after 10 minutes by default; the 24-hour and 30-day maxima; content-free notices for up to 30 days after an account deletion; operator backups; browser push services and ntfy; the cloud AI provider; the manufacturer clouds) and name the Billing consequences only where `GET /api/v1/billing/status` finds Billing.

### 10. Delete me (step 3)

**The API.** `DELETE /api/v1/identity/me`, body `{"password"}` or empty after a step-up, as section 2 says: a login session, confirmed with the password or a recent step-up (401 `reauth-required`); API tokens and service identities get 403 `step-up-unavailable` before anything is looked up; a wrong password counts as a failed login of the user. The server applies the operation of the caller's role (`self_deletion` in `identity.domain.erasure`), so the client needs one call and reads the answer:

| Caller | What happens | Answer |
| --- | --- | --- |
| A member without the owner relation (sub-users and admins included) | the user is deleted at once and for good | 200 `{"operation": "user", "account_id", "delete_after": null}` |
| The owner | exactly `DELETE /accounts/{id}` (section 1 and 3): 409 while other members exist or the account is already scheduled, else the grace period starts | 202 `{"operation": "account", "account_id", "delete_after"}` |

Decided here, because the earlier sections left it open:

- **No grace period for a member.** The grace period exists because an account deletion destroys the account's data. A member's deletion destroys nothing of the account (what the member created belongs to the account and stays), so there is nothing to restore; an admin can create the sub-user again. The dialog of step 4 must say that it is immediate.
- **An owner is never deleted as a user**, also not through this endpoint: an account without an owner cannot exist and there is no hand-over (section 1). The use case that deletes a user checks the rule again inside its transaction and answers 409 with "delete the account instead (`DELETE /api/v1/identity/accounts/{account_id}`)".
- **While the account is `deleting`** its owner is the only member (section 3), so the call can only be the owner's and answers the 409 "already scheduled" of step 1; the owner cancels with restore. The **last member besides the owner** may leave like any other; afterwards the owner can delete the account.
- **The username and the e-mail address are free again**, as after an account erasure: the user row is deleted, nothing reserves a name.
- **The demo** refuses the call like every other change of an account (403 `demo-mode`; the route is not on the demo policy's allow list).

**What Identity removes**, in one transaction (`UserService.delete_self`): the user row; sessions and refresh tokens, passkeys and open ceremonies, linked providers, app login codes, known devices, the tour progress and the login attempts under the username (`delete_user_rows`, the one list of a user's rows, now shared by the removal of a sub-user, "delete me" and the account erasure); the membership and the role assignments, with the tuples reconciled away before the commit (503 and nothing deleted while OpenFGA is down); the user's personal access tokens and widget credentials (revoked, then deleted). API tokens the user created for the account are revoked and stay listed, as when an admin removes a user. The audit rows stay (section 6, "One user"); the last one is `user.self_deleted`. Identity refuses every access token of the user at once, and since section 12 so does every other service: `identity.access.revoked` puts the user and their API tokens on the deny list of the token verification before `identity.user.deleted` goes out.

**How the other services learn: the existing event `identity.user.deleted`** (stream `EVENTS`, payload `UserChanged`, `reason: "self"`), not a request like `account.erase.<service>`. Since section 11 the event carries the opaque user id and no user name (a fixed placeholder stands in the field for one release, see there). An account erasure must be confirmed before Identity deletes its own rows, because afterwards nobody could ask again, and it removes data whose loss must be certain. A deleted user leaves an account that goes on, the same thing happens when an admin deletes a sub-user (which has always published this event), and Notifications and Vision already consume it; a second mechanism for the same fact would have to be kept in step with the first. JetStream keeps the event until each durable consumer acknowledged it, and a consumer that could not finish gets it again. The one gap is Identity's publish after the commit (it has no outbox): an event lost there would leave the name in the other services while the user is gone from Identity. That holds for every Identity event and is an open point for the maintainer, below.

**What a service does** is the kit's `UserErasure` (`mowdeck_service_kit.user_erasure`), the counterpart of `AccountErasure`: the service's `forget`, then a count of what is still personal, and `UserErasureIncomplete` (the event comes again) while something is left. What is personal is read from the schema: tables with a `user_id` column are a user's own rows, and a JSON column named `owner` or `<verb>_by` stores a `PrincipalRef`, which carries the person's `display_name`. A plain id stays, as section 6 says.

| Service | On `identity.user.deleted` |
| --- | --- |
| Fleet | scrubs the name in `commands.issued_by` and `drive_sessions.started_by`; rows and ids stay |
| Scheduler | scrubs the name in `schedules.owner` and `schedule_runs.issued_by`. The schedule keeps its owner's id: the firing re-checks the owner's right, finds none, skips and then disables the schedule with its reason, as for an owner who lost the right; whoever re-enables it becomes its owner |
| Telemetry | stores no name and no row of a user. It revokes the tracking share links the user created (a link works without signing in, and a person who is gone must not keep one), as Identity revokes the API tokens a removed user created |
| Planner, Entitlements, Billing | nothing: plain ids only (`templates.created_by`), `plan_history.actor` is the subject id of the platform operator or the name of a service |
| Notifications | deletes the user's rows in all ten tables with a `user_id` column (its handler from before this ADR). Follow-up after step 2b: onto the kit's use case |
| Vision | deletes `user_providers` and `user_preferences` (its handler from before this ADR). Follow-up after step 2b: also `provider_requests` and the names in `proposals.requested_by`, `approved_by`, `decided_by` |

A guard test (`tools/repo-checks/tests/test_user_erasure_registry.py`) reads every service's schema: a service that stores something personal of a user must have the user erasure's adapter (`adapters/bus/user_erasure.py`) or be listed in `USER_PENDING` (Notifications and Vision, until the follow-up of step 2b); the list only shrinks.

**For step 4:** `GET /me` says in advance what the call will do: `memberships[].self_deletion` is `user`, `account` or null (refused, section 1), from the same domain rule the call applies, next to `is_owner` and `account_status`. The dialog names the operation before the call and reads `operation` after it; there is no dry run and none is needed. An owner's call is audited as `account.deletion_requested` on the account, a member's as `user.self_deleted` on the user, so the log never leaves open which of the two happened. For `user` the client leaves like after a sign-out (the refresh cookie is already dropped); for `account` it stays signed in and shows the banner of section 3. The text for a member must say: immediate, no way back, what you created stays with the account without your name, schedules you own stop until somebody else takes them over, share links you created stop working.

**Open points for the maintainer:** (1) Identity publishes its events after the commit without an outbox; an outbox would close the gap named above for every event. (2) A person an admin *removes* from an account (`DELETE /accounts/{id}/users/{user_id}`, not a sub-user) still keeps their user row, as the Context describes; deleting that row is not part of "delete me". The list of everything still open after the fix before step 2c is at the end of section 12.

### 11. The message streams (fix before step 2c)

Deleting rows is not enough: JetStream keeps messages for the retention of their stream, and a service that fills a view from a stream on start reads them again. The reviews of steps 2b and 3 found an erased account's last map coming back into Vision's memory after a restart, notification texts staying 30 days, and a user name in `identity.user.deleted`. Before the purge is switched on (step 2c) both are closed.

**What exists.** Five streams (`mowdeck_contracts.v1.subjects.STREAMS`), created by the `nats-streams` job. There is no key-value bucket and no object store anywhere in the code (a guard test keeps it that way, below). The retention is quoted from the stream definitions.

| Stream | Subjects | What the messages hold of an account | Retention | Who reads it back | Removed by |
| --- | --- | --- | --- | --- | --- |
| `COMMANDS` | `command.mower.<id>`, `command.result.mower.<id>` | the account id, who issued the command (`issued_by` with the display name), spot targets as coordinates, free text in results | `max_age_seconds=24 * 3600` (1 day), 256 MiB | Device-Gateway, Fleet, Telemetry, Notifications, Vision, Realtime | Fleet, purge by subject |
| `TELEMETRY` | `telemetry.mower.<id>` | the position of the mower and of the base station, error texts | `max_age_seconds=3600` (1 hour), 1000 per subject | Scheduler, Telemetry, Notifications, Realtime; Vision and Camera-Relay replay the newest state of every mower on each start | Fleet, purge by subject |
| `DEVICE` | `device.mower.<id>.map`, `.capabilities`, `.path` | the map of the garden (area names, polygons, the geographic origin), the route of the running job | `max_age_seconds=30 * 24 * 3600` (30 days), 1 per subject | Vision and Realtime replay it on **each** start; Notifications, Planner and the Scheduler when their consumer is first created; Telemetry | Fleet, purge by subject |
| `CAMERA` | `camera.mower.<id>.relay.<kind>` | the account id, who started or requested a camera session (display name) | `max_age_seconds=30 * 24 * 3600` (30 days), 64 MiB | Fleet | Fleet, purge by subject |
| `EVENTS` | `event.<domain>.<name>` | notification titles and bodies, mower and area names, tracking positions, the account name, the device and network of a new login, display names in principal references | `max_age_seconds=30 * 24 * 3600` (30 days), 1 GiB | durable consumers that were down resume from their position | Identity, message by message |

**Who removes.** NATS checks the right to purge or to delete a message per *stream*, not per subject: the filter of a purge and the sequence of a delete are in the request body. Whoever may remove from a stream can remove anything in it, so the right cannot go to every publisher, and ADR 0074 gave it to nobody. It now goes to exactly one service per stream, the one that owns what the stream's messages are *about*:

- **Fleet owns the mowers** (`mowdeck_contracts.v1.fleet`: "Fleet owns the mowers"). The four streams whose subjects carry the mower id (`MOWER_STREAMS`) are purged by subject filter. The publishers of those subjects (the Device-Gateway, Realtime, Vision, the camera relay) get no such right.
- **Identity owns accounts and users.** `event.<domain>.<name>` names neither a mower nor an account, so nothing of one account can be addressed by a subject filter in `EVENTS`; the envelope names the account (`EventEnvelope.account_id`, and every account event's payload repeats it). Identity reads the stream message by message and deletes single messages. Changing the subject scheme of every event to carry the account was the alternative; it would have touched every publisher and consumer and every durable consumer's filter, for the same result.

The shared part is in the kit, once: the port `StreamStore` (`mowdeck_service_kit.bus`) with `purge_subject`, `count_subject`, `stored_messages` and `erase_message`, implemented by `JetStreamBus` (a filtered `STREAM.PURGE`; stream info with a subject filter; a batched direct get, `DIRECT.GET` with `next_by_subj`, 500 messages per request, between two sequences: no consumer, the next batch is asked for only when this one was handled, so no overrun whatever the stream's size, and a read can stop and continue; the newest sequence of a stream from the stream info; `STREAM.MSG.DELETE`, which overwrites the message) and by `InMemoryBus` (which now keeps what its streams hold). It is not part of `EventBus`: a service that only publishes and consumes never sees it.

**A removed mower** (`mower.removed`, whoever caused it: the API, a linked account that went, a demo sandbox, the account erasure): Fleet consumes its own event with the durable consumer `fleet-mower-streams` and purges the five subject filters of the mower (`fleet.adapters.bus.streams`, the port `MowerStreams`). A purge that fails is delivered again.

**An erased account, Fleet's part.** Fleet's `AccountErasure` now purges the streams of the account's mowers inside the request, **before** the row purge (the rows still say which mowers the account has; a purge that fails leaves them, so the next attempt knows the mowers again) and **after** it (what a mower still sent until the Device-Gateway closed its connection). Messages still counted on those subjects afterwards are reported like rows that remain (`ErasureIncomplete`, "stream messages: n"): Fleet does not confirm while a message is left. `AccountPurge` (the purge of the demo sandboxes) is unchanged; a sandbox's mowers are covered by `mower.removed`.

**An erased account, Identity's part.** After the last service confirmed and before Identity deletes its own rows, the purge removes every stored event whose envelope or payload names the account (the rule is `event_names_account` in `identity.domain.erasure`). A failure is the step `event_stream` in the record: the account stays `purging` with its rows, the attempt is repeated with backoff, and no service is asked again. The number of erased events is in the `account.erased` audit row.

**Reading `EVENTS` finishes at any size.** The stream holds every account's events of 30 days, so finding one account's or one user's events is a long read on any installation with more than a few accounts. A first version read it in one go, one request per message (about 750 messages per second), inside the delivery of `identity.user.deleted`: above some 20 000 events that exceeded the 30 s acknowledgement wait, the event was delivered again and the read started over, so it never finished. Now (`identity.application.event_erasure.EventErasureService`, the port `EventLog`, the adapter `BusEventLog`):

- *A record, not a delivery.* The work is a row of `event_erasures` (migration 0013; ids and counters, deleted when the work is done). `identity.user.deleted` (durable `identity-user-events`) writes the row and runs one slice; the delivery is acknowledged then, whatever is left.
- *Slices.* One call reads for at most 10 s (`EventBudget`), stores its position and returns. A background task of Identity carries on for users. The purge of an account takes one slice per attempt and is due again at once, so a long read holds the attempt's five-minute lease for 10 s and the other purges of the same sweep get their slice in between.
- *Resumable.* The row remembers the subject filter and the last sequence read. A restart, another replica or a failure in the middle continues there; nothing is read twice.
- *It ends.* The row remembers the stream's newest sequence when the work began and nothing above it is read. What is published later cannot be the account's (every service confirmed before) or the user's (the user is gone), so traffic cannot keep the read alive.
- *Only what can name somebody.* The subjects read are `EVENT_FILTERS` (the events with names, texts, positions, a device). `OPAQUE_EVENTS` are skipped: `identity.grants.changed`, `identity.api_token.revoked`, the deny list entries and `entitlements.plan.changed` carry ids only and are most of the stream. A repository check fails for an event type of the contracts that is on neither list.
- *Batches.* `EVENTS` now allows direct gets (`StreamSpec.allow_direct`; the `nats-streams` job updates the stream). A stream that does not answer them yet is read one message per request, as before.

*Cost,* measured against NATS 2.15 in Docker on a development machine: 40 000 stored events of 300 bytes read, decoded and decided in 8.3 s, with 400 of them erased, about **4 800 events per second** (the bare batched read does about 32 000 per second). Decoding the JSON and the rule in Python dominate, then one request per erased message. A stream of a million readable events takes about three and a half minutes per erased account or deleted user, in 21 slices; two replicas that work on the same row do the erasing twice at worst (it is idempotent).

**A deleted user: the name leaves the events without losing one in any update order.** No consumer ever read `UserChanged.username`, so the field goes. What a consumer of the release before this change (v0.69.1) does with each shape, read from its model (`username: str = Field(min_length=1, max_length=64)`, required) and its handlers (the kit's `user_deleted_handler`, the `identity_handler` of Notifications and Vision: a payload that does not validate raises `DropMessage`, which acknowledges and discards the event), and pinned by a test that feeds that model:

| Event sent | An old consumer |
| --- | --- |
| no `username`, or `null` | **drops it**: the user's rows stay in that service |
| `username: ""` | **drops it** (at least one character) |
| `username: "-"` (any non-empty string) | handles it; the field is never read |
| `version: 2` in the envelope | does not look at the version: only the payload's shape decides, as above |

A Helm rolling update replaces pods in no particular order, so an event without the field would be lost wherever an old consumer pod still runs, and that cannot be repaired afterwards. The removal therefore takes two releases:

1. *This release.* The field is optional in the model, so every consumer from now on accepts an event with or without it. Identity sends the fixed placeholder `-` (`USERNAME_PLACEHOLDER`: not a valid user name, nobody's name) and the event stays **version 1**. Old and new consumers handle it in any order. A test keeps the placeholder in place and checks it against the old model.
2. *A later release,* when no installation runs a consumer of v0.69.1 or older: Identity omits the field and publishes version 2 (`USER_CHANGED_VERSION`).

Identity also erases the stored events that name the user, with the mechanism above: by `user_id` in the payload (the user's notifications, a login from a new device, an `identity.user.created` of before with the name) or by a principal reference (`requested_by`, `owner`). The announcement itself stays, the services still read it; it carries ids and the placeholder.

**A consumer that starts later** finds nothing: the purge removes the messages, not a consumer's position. Tests restart a consumer against the same stream (the kit against a real NATS, Fleet's erasure, Vision's view).

**What remains, and for how long** (this is what the texts of section 7 may promise):

- *Opaque notices.* `identity.grants.changed`, published while Identity deletes its own rows, and `identity.user.deleted` carry random ids and nothing else. They stay until `EVENTS` drops them (`max_age_seconds=30 * 24 * 3600`). Removing them at once would race the consumers that must read them (the authorization caches).
- *A member's display name in two mower streams.* A command names who issued it and a camera event who started it. Those subjects name the mower, and the mower's messages belong to the account, which goes on, so they are not purged when a member leaves. The name ages out with `COMMANDS` (`max_age_seconds=24 * 3600`) and `CAMERA` (`max_age_seconds=30 * 24 * 3600`). Open point below.
- *Late messages.* A state the Device-Gateway publishes after the purge of its mower stays for the retention of its stream (at most 1 hour in `TELEMETRY`, 30 days for a snapshot in `DEVICE`). The second purge of the account erasure narrows this to what arrives after Fleet answered. It is the same open point as late messages that write rows again.

**NATS permissions** (ADR 0074, `tools/repo-checks/scripts/nats_auth.py`): the map has two new columns of an `Access`. `purge` lists the subject filters a service purges (Fleet: the five mower filters) and yields `$JS.API.STREAM.PURGE.<stream>` for their streams; `erase` lists the filters it reads and deletes singly (Identity: `event.>`) and yields `$JS.API.DIRECT.GET.<stream>` (the batched read), `$JS.API.STREAM.MSG.GET.<stream>` and `$JS.API.STREAM.MSG.DELETE.<stream>`. The code scan finds the calls (`purge_subject`, `count_subject`, `stored_messages`, `last_sequence`), so a filter in the code that the map lacks, or the other way round, fails the repository check. Fleet additionally consumes `event.mower.removed`, Identity `event.identity.user.deleted`. Nobody may delete a stream, and no other user may purge or delete a message; the test against a real NATS server checks both directions.

**Guards.** `tools/repo-checks/tests/test_stream_erasure_registry.py`: every stream is a mower stream, or has an owner that erases by envelope, or is listed in `PENDING` with its reason (empty today; the list only shrinks); every subject a service publishes into a mower stream is covered by one of Fleet's purge filters, so a new snapshot kind or per-mower subject fails until it is purged; the owners have the permissions; and no key-value bucket or object store exists in the code. `test_nats_auth.py`: every stream has exactly one user that may remove from it.

### 12. No access token outlives a deletion (fix before step 2c)

Access tokens are signed, verified offline by every service and live for `MOWDECK_IDENTITY_ACCESS_TOKEN_MINUTES` (default 10, at most 15; `IdentityConfig.access_token_ttl`, the value `TokenIssuer` signs with). Ending a session ends the refresh token, not the access token. For a sign-out that is accepted ([ADR 0065](0065-security-center-and-new-login-alerts.md)). For a deletion it was a hole: some rows need nothing but a permission in the token (`PUT /notifications/preferences`, a push subscription: "admitted on the token's `notifications.manage` claim alone"), so a client whose account was just purged, or whose user was just deleted, could store rows again after the service had confirmed it holds none. Both cases are decided in Identity, so every service is covered at once.

**An erased account: the purge waits.** The transition to `purging` (`ErasureService.begin`) already ended every session and removed every tuple, and a purging account gets no token: a login and a refresh are refused (`sessions.py`: only an active account, or a `deleting` one for its owner), an API token cannot be exchanged (the tokens were revoked when the deletion was requested). What remained were the access tokens issued up to that moment. One pure rule in the domain (`tokens_expired_at(ended_at, access_token_ttl, skew)` in `identity.domain.erasure`) says when the last of them has run out: the lifetime, read from the same `access_token_ttl` the issuer signs with, plus `TOKEN_SKEW` (60 s: the 30 s a verifier allows on `exp`, `MOWDECK_AUTH_LEEWAY_SECONDS`, and as much again for clocks that differ). The two numbers are tied, not merely documented: `mowdeck-auth` refuses a leeway above `MAX_LEEWAY_SECONDS` (30) when the settings are read and when a verifier is built, with a message that names the variable, so a service whose verifier would accept tokens for longer than Identity waits does not start; a test keeps `TOKEN_SKEW` at twice that maximum. **No service is asked to erase before that moment.** The record's first attempt is due then, and `advance` checks the rule again from `started_at`, so a record written earlier cannot get around it. With the defaults the purge asks Fleet 11 minutes after it began. The grace period is untouched: while the account is `deleting` its owner signs in, refreshes and acts as before (section 3, the maintainer's decision), nothing is revoked, and restore works.

**A deleted user: a short-lived deny list.** "Delete me" has no grace period and no wait: the user is gone at once, and the services drop their rows as soon as `identity.user.deleted` arrives. Two ways were weighed.

1. *A deny list every service's token verification consults* (chosen). Identity publishes `identity.access.revoked` (`AccessRevoked{scope, id, issued_before, expires_at}`): refuse the tokens of this subject (a user id or an API token id) or of this account that were issued up to `issued_before`, until `expires_at` (`tokens_expired_at` again). It carries ids and times, nothing personal.
2. *Each service delays its handling of `identity.user.deleted` until the tokens have expired.* Simpler, but the deleted person's rows would stay 11 minutes in every service, every service would need the delay, and the texts would have to say so.

There was no mechanism to reuse for (1): `session_ended` is a database lookup inside Identity, and `identity.api_token.revoked` is published but consumed by nobody. What does exist is the pattern of `identity.grants.changed`: Identity publishes on `EVENTS`, a library function subscribes each process with an ephemeral consumer. The deny list follows it:

- **One implementation.** `mowdeck_auth.revocation.RevocationList` (pure, the time injected, bounded) belongs to `JwtVerifier`, which asks it as its last check. `JwtPrincipalResolver` is `BusAware` (a protocol of the kit), and the kit's `create_app` attaches it to the bus before the start-up hooks. A service has no code for it; the eleven services that verify tokens got one line in the NATS map each. Realtime verifies the token of a WebSocket itself and runs a `RevocationFeed` of its own. Identity uses the same resolver, so it refuses those tokens on its own endpoints as well.
- **Every replica, and after a restart.** Each process has its own consumer (no queue group). The event is the one whose subject carries an id below its type (`event.identity.access.revoked.<id>`), so a process that starts later reads the newest entry of every id with the bus's existing `last_per_subject`; entries that have expired are ignored. No new stream, no key-value bucket and no change of the `EventBus` port were needed.
- **Entries expire by themselves** at `expires_at`; nothing has to be removed from the list.
- **What Identity publishes.** For a deleted user (`delete_self`, and an admin who deletes a sub-user or removes a member): one entry for the user and one for each API token that was revoked with them (an access token exchanged from an API token has the token's id as its subject), after the commit and **before** `identity.user.deleted`, so a service refuses the tokens before it drops the rows. For an account: one entry with `scope: account` when the purge begins. That entry is not what the erasure relies on (the wait is), it closes the 11 minutes for everything else a token could do.
- **Nothing changes for a sign-out, a revoked session, a refresh or a disabled user:** none of them is put on the list (tests pin this). Extending the list to them is possible and would be a decision of its own (ADR 0065 lists it as a follow-up).

**Failure behaviour: the list fails open, the erasure does not depend on it.** A service that cannot reach the bus keeps the entries it has and accepts tokens it never heard a revocation of, as before this list existed. Refusing every token while NATS is away would sign everybody out of every service at once and take the emergency stop with it; that is not a safe direction for a machine with blades. So:

- *Account erasure:* the guarantee is hard and independent of the list. Identity itself waits; a service that missed the entry is asked only after the tokens have expired.
- *Delete me:* the guarantee holds wherever the entry arrived. A replica that did not receive it (the bus away, or Identity's publish after the commit lost, the open point of the missing outbox) accepts the deleted user's token until it expires, at most the access token lifetime plus the verifier's leeway (10 minutes and 30 seconds with the defaults), and could store token-only rows of that user again in that window. A replica that is cut off from NATS also has not handled `identity.user.deleted` yet, and handles it when it is back; rows written after that are the residual. This is what the "delete me" text may claim: your access ends at once, and at the latest when your current sign-in token runs out after 10 minutes.
- *Identity's own endpoints after the purge began.* Identity's verifier keeps the list too, so a request with the old access token (for example `POST /accounts/{id}/restore`) now answers 401 where it answered 404 before (no tuple). The web client retries a 401 exactly once after one refresh (`apps/web/src/lib/api/client.ts`); the refresh of a purging account is refused, so the client ends the session (`tokens.expire()`): no loop, the user is on the sign-in page with the "session expired" notice, and signing in again is refused. Tests pin the refused refresh and sign-in.
- A malformed entry is dropped with a warning. The list is bounded (10 000 entries; the oldest go first), so nothing published on the bus can grow a process without limit.
- *The server refuses the subscription itself* (added after the v0.69.4 deploy, where a NATS that still ran the permissions of the previous release refused the new consumer and seven services restart-looped). `RevocationFeed` (`mowdeck_auth.revocation`, used by `JwtPrincipalResolver` and by Realtime) treats a refused consumer like a bus that is away: it logs one error that says what it means, the service starts and serves, the readiness check `token-deny-list` is reported as **degraded** (`/readyz` answers 200 with `"status": "degraded"`, `mowdeck_readiness_check_up{check="token-deny-list"} 0`, the log line "service degraded"), and the feed tries again in the background (5 s, doubling up to 60 s) until it subscribes, then the check passes again. It is a check that is not `required` (a kit feature, ADR 0077): failing the readiness would take the service out of routing, which is the "refuse everything" this section rules out. A bus that is not connected at all is still reported by the `nats` check, and a closed bus ends the retries. Why the server refused it and what `deploy.sh` does about it: [Compose operations](../ops/compose.md#nats-permissions-after-an-upgrade).

**NATS permissions.** `event.identity.access.revoked.*` is a `consume` filter of billing, device-gateway, entitlements, fleet, identity, notifications, planner, realtime, scheduler, telemetry and vision; Identity publishes it under its `event.identity.>`. The Assistant has no bus and no data and verifies tokens without the list. The code scan knows the four entry points (`principal_resolver_from_env`, `JwtPrincipalResolver`, `RevocationFeed`, `subscribe_revocations`), so a service that starts to verify tokens without the permission fails the repository check; a test against a real NATS covers the live entry, the replay after a restart, that no other service can publish one, that **every** user of the map with this `consume` entry creates the consumer exactly as its code does, and that a refused one fails open.

**Open points after this fix.** Resolved: the streams (section 11), the user name in the event, a still valid token writing after the purge or the deletion. Kept, for the maintainer:

1. *Late messages.* A message that arrives after a service erased can write a row again (a state of a mower of the account in Vision's `auto_watch`, a camera photo), and a message published after Fleet's stream purge stays for the retention of its stream. The services cannot tell an erased account from one they have not seen yet.
2. *Memory in other replicas.* The erasure reaches the memory of the replica that answers. Realtime (`Hub._capabilities`, the last state per mower) and the Camera-Relay (the status per mower) never drop a removed mower's entries and consume no `mower.removed`, although the data map above says they are "stopped by `mower.removed`"; their memory ends with the process.
3. *A Live Activity already on the lock screen* is not ended by the erasure (section 8).
4. *Identity has no outbox:* an event lost after the commit (`identity.user.deleted`, a deny list entry) is not sent again.
5. A person an admin *removes* from an account keeps their user row (section 10).
6. *A member's display name in `COMMANDS` (1 day) and `CAMERA` (30 days)* after "delete me" (section 11). Fleet could erase those messages singly, the way Identity does in `EVENTS`; it would need the message get and delete right on both streams.
7. *Sessions that end otherwise* (sign-out, a revoked session, a disabled user) are not on the deny list; their access tokens run out by themselves.
8. *Two replicas of Identity can work on the same `event_erasures` row* (there is no lease on it). Both erase the same events, which is harmless, and the read is done twice at worst.
9. *Two consumers, no order between them.* A service gets the deny list entry and `identity.user.deleted` through different consumers. Identity publishes the entry first, but nothing guarantees that a service applies it first; the window is the delivery time of one message.

Added by step 2c:

10. *No refund.* A subscription of an erased account ends at once and the rest of the paid period is not refunded (section 5). Since step 4 the dialog says so where Billing runs: "when the deletion starts, your subscriptions end at once, without a refund for the rest of a paid period. Your customer record at the payment provider is deleted. Invoices and payment records stay with the payment provider." Whether no refund is right for every plan, and the sentence in the terms, stays the maintainer's to decide; the code issues no refund because this ADR decides none.
11. *Accounts already scheduled when the purge is switched on* get no second grace period and no notice (section 4). A notice to the owner, or a grace period counted from the update, would be a new mechanism.
12. *A Billing that the deployment did not name.* The start-up refusal covers Compose and the chart. An installation that runs Billing some other way and sets `MOWDECK_BILLING_OPTIONAL_SERVICES=billing` without telling Identity is not caught. Identity could ask every erasure service of the contract once and treat "no responders" as "not deployed"; that would also skip a Billing that is merely down, so it was not built.
13. *Customers Billing does not know.* The erasure deletes the customer in Billing's row. A second customer at the provider with the account's id in its metadata (created by hand in the provider's dashboard) is not found.
14. *`identity.account.created` delivered late.* Billing remembers an account's name from that event. A Billing that was down since the account was created and consumes the event after it answered the erasure would store the name again; this is the late message of point 1 for Billing.

## Consequences

- Step 1 changed nothing a running installation did and nothing the web app showed: the purge was off by default, and the grace period behaves as before (the owner keeps every permission). The one change of the API was that `DELETE /accounts/{id}` answers 409 while other members exist.
- **Step 2c changes what a running installation does:** the purge is on unless `IDENTITY_ERASURE_ENABLED=false` is set. A deleted account is really deleted when its grace period is over, and an account that was scheduled while the purge was off is purged at the first sweep after the update (section 4). An installation whose `.env` or values carry an explicit `false` (the line of `.env.example` since step 1) stays off until the operator changes it.
- Billing applies a provider event only to a customer it knows (section 5). An event that names an account in its metadata and a customer Billing never created is dropped, where it was applied before; `python -m billing.cli send-fixture` therefore needs a started checkout first.
- Billing does not start where the deployment did not name it to Identity (section 4). An installation that started it with `--profile billing` on the command line only sets `COMPOSE_PROFILES=billing` in `.env`.
- The App Store requirement (guideline 5.1.1(v)) is met with step 4: deletion starts inside the app, Settings -> Profile. The public demo locks it, so the review notes name an account on another server for a reviewer who wants to run it ([Mobile apps](../ops/mobile-apps.md#app-review)).
- A new service that stores per-account data must answer `account.erase.<service>`, and the guard test fails until it does (this extends the checklist of ADR 0076, which covers the demo only). It wires the kit's `AccountErasure` with its purge and its row count, subscribes in `adapters/bus/erasure.py` and adds the `serve` entry of its NATS user.
- The grace period means an account's data lives up to 7 days after the request plus the purge time; the text must say so. The purge time includes the wait for the access tokens (the token lifetime plus 60 s, 11 minutes with the defaults) before the first service is asked.
- Every service that verifies tokens keeps a deny list fed from the bus (section 12). A new service gets it from the kit without code; it needs the `consume` entry for `event.identity.access.revoked.*` in the NATS map, and the repository check names it when it is missing.
- The PostgreSQL function and trigger of migration 0011 are the only way the audit log is ever changed, and only to remove personal data.
- Two services may remove stored messages (section 11): Fleet purges the four mower streams, Identity deletes single messages of `EVENTS`. This widens what ADR 0074 allowed ("no message get or delete", nobody purges): a compromised Fleet could empty the mower streams (their history is short and the services keep their own), a compromised Identity could read every domain event and delete from `EVENTS`. A new stream, a new per-mower subject, a key-value bucket or an object store fails the stream registry test until it has an owner that purges it.
- The account erasure takes longer for a large `EVENTS` stream: Identity reads the events that can name an account once per erased account, in slices of 10 s (about 4 800 events per second, section 11). Identity has one more table, `event_erasures`, and one more background task.
- A token verifier refuses to start with `MOWDECK_AUTH_LEEWAY_SECONDS` above 30 (section 12): an installation that had raised it must lower it again.

### The split

1. **Contract and Identity core** (this step): the contract and subjects, the state machine, the purge job and its record, Identity's own rows and tuples, cancel within the grace period, the audit scrub, the owner block, the guard test with `PENDING`.
2. **Service handlers** answering `account.erase.<service>`: 2a Fleet, Scheduler, Telemetry, Planner and Entitlements (the existing purge classes of ADR 0076 behind the new adapter; **done**, with the shared use case and handler in the service kit); 2b Notifications and Vision (**done**: the same pattern, plus stopping the work in flight); 2c Billing (**done**, section 5: the subscriptions end and the customer is deleted at the provider, Billing is asked before Entitlements, the deployment names it to Identity, and the purge is on by default). `PENDING` shrank with each and is empty.
3. **Member self-removal** (**done**, section 10): `DELETE /identity/me`, the role policy, the user-level cleanup in Fleet, the Scheduler and Telemetry through the kit's `UserErasure`, tests across accounts. Notifications and Vision keep their own handlers of the same event; moving them onto the kit's use case, and what they still leave, is the follow-up listed in `USER_PENDING`.
4. **Web app, docs and e2e** (**done**, section 9): the Settings flow with its states, the banner, the fields of `GET /me` it reads, the privacy template and the operator documentation (backup TODO), the user guide, the Playwright specs, the README.
