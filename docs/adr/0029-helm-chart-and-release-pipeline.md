# ADR 0029: Helm chart and release pipeline

## Status

Accepted (2026-10-10)

## Context

Phase 4 brings the cloud operating mode of the project plan ("Betriebsarten"): the same images as the Compose stack, run by a Helm chart on Kubernetes, PostgreSQL per service or managed, a NATS cluster, a gateway with a public domain, images for amd64 and arm64, non-root and read-only, configuration only through environment variables or secret files, migrations as a separate step before the start, and only standard interfaces (PostgreSQL, S3, OIDC, NATS). Until now the services carried per-service Helm value stubs (`services/*/helm/values.yaml`) that no chart rendered, and CI built amd64 images only, without publishing them. The repository is private and Actions minutes are scarce.

## Decision

**One umbrella chart, `infra/helm/mowdeck`, without MowDeck subcharts.** One template file per service calls shared named templates (`mowdeck.workload`: ConfigMap, Deployment or StatefulSet, Service, optional HorizontalPodAutoscaler and PodDisruptionBudget; `mowdeck.migrationJob`). The services are released together and share settings (NATS, OpenFGA, JWKS URL, image tag), so per-service charts would only add versions to keep in step. The per-service value stubs and the template's `helm/values.yaml` are removed. `values.yaml` uses the variable names of `infra/compose/.env.example` under `config` and `secrets`; a repository test keeps the two files, the Compose services and the rendered containers' settings in sync. Overlays `values-homelab.yaml` and `values-cloud.yaml` cover the two operating modes.

**Third-party infrastructure as optional dependencies.** NATS (official chart, JetStream with file storage) and OpenFGA (official chart, postgres datastore, migration as an init container instead of its default hook job with `k8s-wait-for`) are chart dependencies with `condition` switches, replaceable by external endpoints.

**PostgreSQL: CloudNativePG by default, external as the alternative.** With the CloudNativePG operator installed, the chart renders one `Cluster` with a managed login role per service and one `Database` resource per service owned by it, the same layout as the Compose init script. `postgresql.external.enabled` switches to an existing or managed PostgreSQL. CloudNativePG is an operator under the CNCF with declarative roles and databases, failover and backups to object storage; the Bitnami chart images are no longer freely maintained, and a hand-written StatefulSet would give no failover or backups.

**Migrations as Jobs, never in the service process; pods wait for their schema.** With an external database every service's migration Job is a `pre-install,pre-upgrade` hook ordered by `helm.sh/hook-weight`, reading its URL from a hook Secret. With the in-cluster database the release creates the database itself, which does not exist yet when pre-install hooks run, so the migrations are ordinary Jobs named per release revision. In both modes an init container (`wait-for-schema`) holds every database service until its database carries the newest migration of its image (or a newer one), so no pod runs against an old schema and `helm install --wait` converges. The authorization bootstrap is an ordinary Job per revision that waits for OpenFGA; an init container (`wait-for-model`, the bootstrap image) holds the OpenFGA users until the latest model equals the one of their release, so no pod pins an older model.

**Secrets never defaulted.** Required secrets fail the render with a message naming the key (`required`), unless an existing Secret is named (`existingSecret`). They are mounted as files and passed as the services' `MOWDECK_<NAME>_FILE` settings.

**Ingress resources instead of Traefik CRDs.** Standard `networking.k8s.io/v1` Ingress resources with the Compose path routes work with any controller (Traefik in k3s, cloud load balancers, the Tailscale operator); a second Ingress carries the login paths, so a controller-specific rate limit can be attached by annotation. Traefik's `IngressRoute` and the Gateway API remain possible later without changing the services.

**Device-Gateway as a StatefulSet.** The shard index is the pod index label, the shard count the replica count ([ADR 0013](0013-device-gateway-registry-and-sharding.md)). Autoscaling the gateway waits for a connections metric and a shard hand-over; the cloud overlay documents the intended autoscaler but leaves it disabled.

**Release pipeline: tags only, multi-arch through QEMU, OCI chart in GHCR.** `release.yml` runs for `v*` tags and by hand: every image is built once for linux/amd64 and linux/arm64 with Buildx, QEMU and the GitHub Actions cache, pushed to `ghcr.io/<owner>/mowdeck/<image>` with SBOM and provenance attestations and an SPDX file, the chart is packaged with `appVersion` = version and pushed to `oci://ghcr.io/<owner>/charts/mowdeck`, and a GitHub release gets generated notes. Pull requests run only the cheap `helm` job (lint, template, kubeconform `-strict`, drift test); the kind install test with the acceptance test runs by hand and for tags. Signing with Cosign is documented, not enabled (superseded by the amendment of 2026-10-19).

## Consequences

- Kubernetes and Compose deploy the same images with the same settings; a new service needs a chart template, or the drift test fails.
- The in-cluster database requires installing the CloudNativePG operator once per cluster; the chart does not bundle it (cluster-scoped CRDs and controller).
- In job mode a failed migration does not stop `helm upgrade` by itself; the new pods stay in `wait-for-schema` (and `--wait` times out) while the old ones keep serving.
- Fixed names for the OpenFGA Secret and the NATS and OpenFGA services (subchart values cannot be templated): one MowDeck release per namespace.
- The arm64 half of the Python images is built under emulation and is slow; native arm64 runners can replace QEMU without changing the Dockerfiles. The web app's build stage runs on the build platform.
- Packages in GHCR are private like the repository until their visibility is changed.

## Amendment (2026-10-14): CI pulls the third-party images through a GHCR mirror of the repository

**Context.** The workflows pulled the pinned third-party images straight from their public registries (ECR Public, `ghcr.io`, Docker Hub). The e2e job then failed with `429 Too Many Requests` from `public.ecr.aws` while building the service images: GitHub-hosted runners share their egress addresses, so the anonymous quota of a public registry is shared with every other workflow behind the same address, and a re-run is a matter of luck.

**Decision.** The workflow `.github/workflows/mirror-images.yml` copies every image pinned under "Image sources" in `infra/compose/.env.example` with `crane copy` (all architectures, digests unchanged) to the repository's own package namespace `ghcr.io/<owner>/mowdeck/mirror/<alias>:<tag>` (alias: the variable name without `_IMAGE`, lower case, `-` for `_`). It runs when the list, `infra/mirror-env.sh` or the workflow changes on `main` and in pull requests of the repository, and by hand; it skips images whose digest already matches and retries with backoff. `ci.yml`, `helm-kind.yml` and `release.yml` log in to GHCR with `GITHUB_TOKEN` (`packages: read`; `release.yml` writes its own images anyway), export the mirror references with `infra/mirror-env.sh` (`MOWDECK_IMAGE_MIRROR`) and use them for the postgres service container, the `docker run` commands, the build arguments and the Compose `.env` of the acceptance tests. The images only CI runs (ntfy, stripe-mock) are pinned in `.env.example` as well, so one list feeds the stack, the mirror and the checks. `.env.example` keeps the public images: the mirror is a CI concern, and a home installation pulls the public images unless `MOWDECK_IMAGE_MIRROR` (through `infra/mirror-env.sh`) or single `*_IMAGE` variables point elsewhere. The kind install test still builds locally (`push: false`, `load: true`) and pushes no service image.

**Consequences.** Every workflow that pulls images carries `packages: read` and a login step. The mirror packages must exist before a pull request's CI can pass; a pull request that bumps an image fills them itself (re-run its jobs if they pulled first). The packages hold the unchanged public images, so their digests can be compared with the source at any time; their visibility and their link to the repository are set once in GHCR (`infra/compose/README.md`, "Image sources"). `tools/repo-checks/tests/test_images.py` fails when a workflow pins an image of its own, pulls a listed image from its public registry, or when `infra/mirror-env.sh` names an image differently from the list.

## Amendment (2026-10-19): releases by semantic-release on the 0.x line, signed and with provenance

**Context.** Releases were cut by pushing a `v*` tag by hand; nothing tied the version to the changes, the tag was unsigned, and the images, the chart and the release files were neither signed nor attested (the Signing paragraph above left it documented only). The owner's other repositories release with semantic-release through the shared `lukislp/ci-workflows` actions.

**Decision.** `release.yml` runs on every push to `main` instead of on tags. The job `version` runs semantic-release (`lukislp/ci-workflows` action `semantic-release`, configuration `.releaserc.json`, Conventional Commits with the angular preset) as a dry run; the job `tag` runs it for real and creates the tag and the GitHub release with the generated notes; the build jobs then build from that tag, and the job `publish` attaches the files. There is one GitHub release per version, owned by semantic-release; the workflow only adds assets and appends notes. The version line starts at 0.x from an initial tag `v0.0.0`, and on 0.x a breaking change is a minor release (`releaseRules`), so 1.0.0 is a deliberate configuration change; the workflow refuses to release without a `v*` tag. The tag is an SSH-signed annotated tag (`tag.gpgSign` with the repository secret `DEPLOY_SIGNING_KEY`, tagger the owner's noreply address); the deploy key `SEMANTIC_RELEASE_DEPLOY_KEY` pushes it, so the tag still starts `helm-kind.yml`. Every image index and the chart are signed keyless with Cosign and attested with `actions/attest-build-provenance` (pushed to GHCR); the release files get `SHA256SUMS`, a Sigstore bundle each and one build provenance bundle (`mowdeck-<version>.intoto.jsonl`). The version is still set at build time only, so releases make no commit and need no ruleset bypass. By hand the workflow builds a test version without tag or release.

**Consequences.** The commit type of every merged change decides the release, so `CONTRIBUTING.md` treats it as part of the change. A job that fails after `tag` leaves a release without all assets until its jobs are re-run. Verification is documented in [Releases](../ops/release.md#verifying-a-release) and `SECURITY.md`, and OpenSSF Scorecard's Signed-Releases check finds the signature and provenance files on each release.
