# Phases and gates

Each phase ends with a gate: the next phase starts only when the criterion is met. After roughly 8 to 12 weeks the own app should replace the Mammotion app for the owner household.

| Phase | Name | Content |
| --- | --- | --- |
| 1 | Foundation | Monorepo, Compose stack, Identity (accounts, sub-users, roles), OpenFGA authorization, Fleet, Device-Gateway with a simulated mower, Telemetry, Realtime, tenant-isolation tests, spike document |
| 2 | MVP | Real mower control through PyMammotion, status and map, start/pause/dock, cut height and speed, connection choice, notifications, web app (PWA) |
| 3 | Comfort | Home Assistant (HACS) integration, schedules, rain pause, health history, joystick driving, RTK signal map, theft alarm, more users and themes |
| 4 | Fleet & Subscription | Sites, groups, fleet map, bulk commands, reports and fleet API, Billing, Entitlements, operator console, Kubernetes/Helm |
| 5 | Spot & Camera | Spot mowing with pluggable mowing patterns, re-mowing missed spots, live camera |
| 6 | AI | Vision service: Ai Recover and Find Dock |

## Phase 1 acceptance criterion

`docker compose up` starts all foundation services (Gateway/Traefik, Identity, OpenFGA, Fleet, Device-Gateway, Telemetry, Realtime, NATS, PostgreSQL); a user registers, creates a sub-user with the Operator role, registers a simulated mower, sends start/stop and sees live status over WebSocket; a user from a foreign account is rejected everywhere, backed by tests; the spike document exists.

## Phase 2 acceptance criterion

`docker compose up` serves the web app at `/` (service `web`) next to the API. In the installed PWA (German by default, English available), an owner registers, registers a mower, sees it docked with battery, RTK fix and connection, starts a chosen zone, follows the mower live on the map with its driven route, changes blade height and speed while it mows, pauses, resumes and sends it back to the dock; a Viewer sees status and the emergency stop but no start control; a user of another account sees nothing; push notifications arrive for "finished", "stuck", "battery low" and "offline". All of this is backed by the Playwright suite `tests/e2e-web` (CI job `e2e-web`) against the simulated mower; it covers the gate steps 1 to 11 of the [web app design](dev/design-web-app.md) (section 8.2): registration, mower registration, live status, areas chosen on the map and started, the live map (the mower chevron moves, the driven route has at least two points), blade height while mowing, return to dock, the Viewer, the foreign account, language and theme, logout; plus notifications (preferences and an ntfy target saved, the test notification answered 202 then 429, the unread badge, a finished simulated job in the inbox) and the connection forms (kinds from Fleet, cloud validation, a `ble_bridge` mower whose noise key is shown as set and never echoed). Web Push delivery through a real push service is checked by hand on the owner's phones (headless Chromium has no push service). The adapter package `mowdeck-control-mammotion` is ready for the hardware test: it passes the `MowerConnection` contract tests, the connection kind can be switched in the app, and a documented hardware test checklist exists. The hardware test itself (the household LUBA replaced the Mammotion app for one week) closes the phase.

## Phase 5 acceptance criterion (proposed)

1. In the web app an owner draws a spot inside an area of a simulated mower (or picks a whole area), chooses a pattern or a chain from the registry with a settings form built from its JSON Schema, sees the preview (paths, duration, area, warnings, execution mode) and starts it; the simulated mower mows along the plan with the blades off on every transfer.
2. After the run, "re-mow gaps" shows the gaps computed from the position track and starts a `remow` plan for them; the coverage afterwards is above 95 % of the mowable area.
3. A template ("2 border laps + diagonal") is saved, listed and started; a Viewer sees previews but cannot start or save; a user of another account sees nothing.
4. A plan that would leave the area, cut through a no-go zone or turn tighter than the mower can is refused with the validation chain's reasons; a mower without `custom_paths` gets only plans with a native job, everything else is refused before it reaches the mower.
5. With billing enabled a plan without `spot_mowing` gets 403 `feature-not-in-plan` from the Planner and from Fleet.
6. Live camera: criterion of the camera task (stream path, latency, access control).
